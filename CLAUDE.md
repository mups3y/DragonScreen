### The four architectural facts a new session needs

1. **`FlightDriver` is a flight-scene `KSPAddon` and drives everything.** Autopilot, booster
   recovery, station approach, docking, undock, de-orbit, node executor, impact predictor,
   recorder. It exists because all of that used to be ticked from `ScreenPainter`, which belongs to
   the IVA — so `ForceSetActiveVessel(booster)` destroyed the thing flying the booster.
2. **`AttitudeController` is an instance class, one per vehicle** (`.Ascent`, `.Booster`), and it
   owns throttle and all three translation axes through each vessel's own `FlightCtrlState`.
   `FlightInputHandler.state` is the FOCUSED vessel's and is cosmetic only. This is what lets both
   vehicles fly at once.
3. **`NodeExecutor` is the one burn mechanism**, and `StNodeSafe`'s periapsis floor lives inside it
   so no caller can forget it. Five things use it.
4. **`ImpactPredictor` + `pure/Trajectory.cs` are ours**, not Trajectories. Drag is MEASURED from
   each vehicle's own telemetry (`a_total − a_gravity − a_thrust` → ballistic coefficient), not
   modelled. Where it cannot measure, it reports a vacuum solve and SAYS so.

### The recorder is 145 columns and checks itself
`a_` = ascent vehicle, `b_` = booster, `r_` = the return, `m_` = the middle of the mission
(rendezvous, dock, undock), all every row, plus `focus` and `warp`. It counts its own commas against the header on
the first row and logs `RECORDER COLUMN MISMATCH` if they differ — **if you see that, do not read the
CSV.** Flight data is archived to `Desktop/quarantine/dragonscreen_flightdata`, not left in the game
folder.

**The two columns that judge a return:** `r_liftMin` — zero at touchdown means the entry flew OPEN
LOOP, so the miss is de-orbit AIM error and not guidance error — and `r_bcAscent` / `r_bcBooster`,
the measured ballistic coefficients everything downstream of a prediction rests on.

### ⛔ 2026-08-10 — SIX DEFECTS FOUND WITHOUT FLYING. READ THIS BEFORE THE NEXT FLIGHT.

The repo was published for outside review. Of ten findings returned, **two were false positives and
three were already documented in the code** — but verifying them turned up worse. Full account in
commit `52f5ce9`; the three that generalise:

**1. "Conservative" was a lie the comment told.** `AvailableTorque` counted reaction wheels only,
and its own comment claimed RCS was included. Measured: 9.5 kN·m of wheels against a recorded pitch
MoI of 21 949 t·m², giving a rate limit of **0.05 °/s where the gravity turn needs 0.45**. The next
flight would have rolled fine and simply refused to pitch over. Nine Merlin gimbals counted as zero.
→ *A comment that describes intent rather than code is worse than no comment; it is what let this
survive several readings.*

**2. Flight software was living inside a display widget.** `BoosterRecovery.Tick()`'s only caller
was `ScreenPainter.Update()`. The painter belongs to the Dragon's IVA, and `ForceSetActiveVessel`
despawns that IVA — so **the very call that starts a recovery removed the thing that flies it.**
Booster fell unguided, `Finish()` unreachable, `Active` stuck true for the session. Now in
`FlightDriver`, a flight-scene `KSPAddon`, which is how MAS scopes the same problem.
→ *Ask what destroys the object your loop lives on. IVA-scoped code cannot survive a vessel switch.*

**3. The vehicle was not the vehicle I assumed.** The Tundra first stage is **ONE part with THREE
mutually exclusive `ModuleEnginesFX`** — AllEngines 2560, ThreeLanding 1706, CenterOnly 764 kN, and
those are *not* multiples of one engine. `Read()` summed all three (5030 kN) and `SetEngines` sorted
three modules at the same position and lit an arbitrary prefix. The landing solve believed a
one-engine thrust of 1676 kN against a real 764 — ignition too low, into the pad.
→ *Read the part config before writing code that commands the part.*

Also fixed: `MaxStoppingTime` leaking 0.05 into the next vehicle, `FindBooster` accepting debris,
grid fins never deployed, entry burn lighting three engines at once instead of the 0.75 s soft start.

### ⛔⛔ THE PORT RULES — READ BEFORE WRITING ANY LINE OF FLIGHT LOGIC ⛔⛔

Written 2026-08-11 after a session in which every single flight failure had one cause: **I took
F9I's numbers and wrote my own mechanism.** F9I is 971 lines that already land a booster 0.34–0.56 m
from the pad. Nothing in this project needs inventing. It needs transcribing.

**RULE 1 — NO FLIGHT-LOGIC FUNCTION WITHOUT A CITED SOURCE.**
Before writing a function that decides anything in flight, name the F9I function it comes from and
put `SPACEX/BOOSTER.ks:394-518` (or wherever) in its doc comment. If there is no F9I equivalent:
**stop and say so to the user.** Do not fill the gap with something reasonable. Every gap I filled
with something reasonable — the 20° boostback pitch-up, the closing-speed miss estimate, the
launch-pad-as-landing-zone, the 200 m clearance hold — cost a flight.

**RULE 2 — PORT THE SEQUENCE, NOT THE CONSTANTS.**
Copying `wait 2.5` and `32500` while writing your own control flow around them is cargo cult. The
2.5 s means something because of what runs before and after it. Read the whole function top to
bottom, including its comments, and reproduce its ORDER. If the port has a different shape from the
original, it is not a port.

**RULE 3 — IF F9I COMPUTES IT, DO NOT ESTIMATE IT.**
F9I gets its impact point from Trajectories. We cannot take that dependency — so the honest answer
is "our predictor is drag-free and therefore predicts long", stated at the call site, NOT a
different algorithm that looks close enough.

**RULE 4 — ONE CHANGE PER TEST FLIGHT.**
Five changes went into the flight that caught the upper stage. When it failed, nothing could be
attributed. A flight costs the user real time; spend it resolving one question.

**RULE 0 — `docs/PORT_PLAN.md` IS THE ORDER OF WORK. FOLLOW IT.**
It names, for every remaining item, the exact functions to read and what each piece consumes and
exposes. The waste on this project has not been porting - it has been rewriting things written
before their dependency existed or before the whole source function had been read. If a read
turns up a dependency the plan does not list, **stop and update the plan first**; discovering
that in code is how a rewrite starts.

**RULE 5 — THE PORT MAP ENTRY COMES FIRST.**
Write the `docs/F9I_PORT_MAP.md` row — source function, line range, what differs and why — BEFORE
the code. If the "why" cannot be written down, the difference is not a decision, it is a guess.

**HOW TO TELL YOU ARE ABOUT TO BREAK THESE:** you are reasoning about what the vehicle *should* do
from physics. Stop. F9I already answered it, and it answered it against flights you do not have.

### ⛔ AN EXCEPTION IN `OnFlyByWire` IS INVISIBLE AND INFINITE

KSP calls it from `Vessel.FeedInputFeed` and **swallows whatever it throws**. The flight continues,
the vehicle simply is not steered — once per physics tick, forever. From the cockpit it looks like
the autopilot doing nothing. It wrote **119 000 log lines in four minutes** and I still had to go
looking for it.

Anything hooked to `OnFlyByWire` must catch, **detach**, and log ONCE.

**And the cause is the recurring mistake in one line:** MechJeb's source reads
`MathExtensions.Euler(-90, 0, 0)` — *its own* implementation. I substituted `QuaternionD.Euler`,
assuming equivalence. **MechJeb wrote its own BECAUSE KSP's is broken** (`Internal_FromEulerRad` is
missing). Use the float `Quaternion.Euler`.

That is the same failure as `"K1"` from a PAW title and `staticAmbientTemperature`: **read the source,
saw a call, substituted the assumed equivalent.** When porting, port what is written — and when the
original uses its own helper instead of the obvious engine call, that is a fact worth understanding
before replacing it.

### SECOND FLIGHT 05:42 — the cameras were inside the hull. ANCHOR, NOT MAGNITUDE.

The user spotted it: the forward view showed the *back face* of the docking port, the side views looked
out through the Draco pods. Cause was `rt.position + fwd * 0.5f` — half a metre from the vessel
CONTROL POINT, which is the middle of a 4 m capsule.

**The fix was not a bigger number, and the two docking-camera mods already installed here prove why.**
`HullCameraVDS/MM_Scripts/DockingPortCameraPatch.cfg` offsets by `cameraPosition = 0, 0.07, 0` and
`0, 0.12, 0` — *centimetres* — and DockingCamKURS parents to `_moduleDockingNodeGameObject`. Their
offsets are tiny because their anchor is the port's own part transform, already at the outside face.
Ours cannot use that anchor: the control point is usually the POD, not a port.

So `DockingCamRenderer.HullExtent` **measures** instead — the control part's renderer bounds projected
along the view axis, plus a 15 cm standoff. Only geometry inside the camera's own culling mask counts,
which excludes the IVA interior without hard-coding a layer number. **The control part ALONE, never the
whole vessel** — off the pad the stack runs 40 m to the engine bells and a whole-vessel extent would
throw the rear camera below the rocket. Cached, refreshed twice a second.

Free corroboration: both mods set `cameraForward = 0, 1, 0`, independently confirming +Y is the docking
axis, which is what `rt.up` rests on. **When a placement looks wrong, check the anchor before the
distance — and check whether an installed mod has already solved it.**

### THE NAVBALL WAS TRANSPOSED, NOT ROTATED — settled 2026-08-06, offline

The ball was 90° out, as feared. The cause was **not** MAS's quaternion — that ports correctly. It
was the texture. `navball_edited.png` is **a standard navball stored on its side**: its U axis is
pitch and its V axis is heading. Measured over the file, not eyeballed:

    light/dark halves split across U, not V   48.9 vs 117.5 left/right, 82.7 vs 83.7 top/bottom
    rows y=16..2032 pixel-identical           content barely varies with V
    every glyph rotated 90 degrees
    a light border ~6 px wide on all sides    lands ON the poles once latitude runs along U

Fed the ordinary (longitude, latitude) unwrap it put the horizon on a *meridian*, so the ball split
vertically and rolled with heading. The fix is in the mesh UVs, not the quaternion.

**`plugin/build/navball_preview.py` is how it was settled, and it is the durable part.** It renders
the ball offline with the same mesh, texture, quaternions and ortho camera as the game, and its
`selftest` reconstructs a real logged attitude and reproduces the euler angles KSP printed **to
0.14°** — so its renders can be believed. All four candidate unwraps were rendered across six
attitudes plus a heading sweep; exactly one has sky up, the ladder upright, readable glyphs, and the
markings sweeping the right way under yaw. **Zero restarts spent guessing.** Two lessons worth
keeping: compare *rotations*, not euler triples, near gimbal lock — straight-up pitch is exactly
there and (270.6, 90.1, 270.0) and (270.7, 360.0, 0.0) are the same attitude; and when a ported
constant looks wrong, check the *asset* before blaming the maths.

**Pipeline:** `python plugin/build.py [test|preview|install]`. `preview` renders **eleven** PNGs —
every page AND every subview, because anything reachable by a control needs its own render. It has

### FLIGHT'S STEP LIST — built 2026-08-06. **THERE IS NO LAUNCH BUTTON, AND THAT IS CORRECT.**

Researched 2026-08-06 and it settles a design question rather than just filling a placeholder: the
countdown is run by the **SpaceX Launch Director**, who gives two explicit gos — propellant load, then
liftoff. Once the hatch shuts the escape system **monitors autonomously**, and during ascent **SpaceX
mission control calls the abort-mode switches**. The crew do checks beforehand and monitor throughout.

**So the console has no launch control, because the real one has none.** A headless test asserts no
step is ever labelled LAUNCH / GO FOR LAUNCH / START LAUNCH / IGNITION — worth failing a build over,
because adding one would hand the crew an authority they do not have.

`pure/StepList.cs` holds 15 milestones with the real T− references (NASA Crew-10, converted against a
7:03 pm liftoff). **The times are display only and advance nothing** — a Kerbin flight will not match
an ISS profile, and a list driven by a clock is confidently wrong the moment a countdown holds.

**Two kinds of step, and the split is the honesty rule applied to a checklist.** OBSERVED steps read
the vehicle (crew, propellant, clamps, MECO, staging, nose cone). CREW steps are tapped to confirm —
comm check, seat rotation, suit leak check, hatch close — because stock KSP has no hatch, no suit and
no intercom. A ticked checklist item is *not* a faked reading: on the real vehicle these are crew
actions, performed and reported. Inferring them from something unrelated would have been the lie.

Liftoff is **the clamps letting go**, not a clock and not an altitude. Every countdown step closes out
once airborne whether or not it was ticked — nagging about HATCH CLOSE at 40 km is not tracking a
mission. A new vessel (stage, undock, revert) resets the ticks.

#### ⛔ FOURTH FLIGHT 16:58 — SEVEN FAILURES, ONE ROOT CAUSE: a chain of `if` instead of `else if`

The whole mission failed, and every failure descends from two lines of the transition block.

**ROOT CAUSE.** The transitions were plain `if`s, so more than one could fire in a single call. On
the tick apoapsis crossed 60 km the first set `phase = Meco` — and the next then read
`PhaseElapsedS`, which was still the **eighty seconds spent in GRAVITY TURN**, decided the 2.5 s MECO
hold was long over, and advanced to `BurnToApoapsis` in the same call. **MECO never happened.** It
was never logged, never held, never staged.

**A state machine must advance ONE step per tick, or a per-phase timer is meaningless — it may be
timing a phase that has already been left.** The chain is now `else if` and that is load-bearing.

The cascade, in order:

| # | failure | consequence |
|---|---|---|
| 1 | MECO phase skipped | — |
| 2 | no stage command ever issued | booster stayed attached all flight |
| 3 | no separated booster existed | **booster recovery never ran at all** |
| 4 | `SecondStage` stayed false | the FIRST-stage pitch law ran the entire flight |
| 5 | that law floors at MECOangle **45°** | the vehicle burned at 45° from 60 km to 129 km |
| 6 | burning 45° above the horizon | apoapsis rose, **periapsis never moved: −598.4 → −597.7** |
| 7 | `CircDvFlipped` read as success | **"INSERTION COMPLETE" announced on a suborbital lob** |

**Two secondary fixes, because #7 is its own class of bug.** `circDv` ROSE from 2098 to 2174 m/s
while the burn ran — it was diverging, not overshooting — and the direction swung past 90°, which
the overshoot test read as "burned past it". So:

- a reversed dv **above 5 m/s** is now an **ABORT with a stated reason**, not a completion;
- `Circularised()` asks the only question that matters — **is periapsis above the atmosphere** —
  because every individual condition that fired was defensible and none of them checked that.

**A false success is worse than a failure**: it disengages and hands back a vehicle nobody is flying.

#### ⛔ THIRD FLIGHT 13:36 — IT LEFT KERBIN. The circularisation had no fixed point.

Ascent was right again (`COAST ap 86.0 km` on the nose). Then CIRCULARISE burned the booster dry,
staged, burned the second stage dry over 2m12s, and the vehicle ended up on an **escape trajectory**.

**Root cause: burning PROGRADE until periapsis reaches a target has no fixed point.** Prograde thrust
raises apoapsis faster than periapsis, so the cutoff recedes as you chase it. It can only ever end by
running out of propellant.

F9I solved this and says why, at `F9_payload.ks:265` (`FalconCircBurnVecNow`):

> "Make the orbit circular HERE, NOW" … This has a **true fixed point** (dv → 0 exactly when the orbit
> is circular at the current radius), so the closed loop **converges by construction** instead of
> chasing a target that has expired.
>
>     dv = (horizontal_unit × sqrt(mu / r)) − v

Ported exactly. Three changes, and all three were needed:
1. **Steer along the dv, not prograde.** Near apoapsis they differ by degrees, and prograde is what
   raises apoapsis instead of periapsis.
2. **Throttle on |dv|**, full at 25 m/s to go and easing to a 5% floor — a full-throttle finish
   overshoots between ticks and cannot be taken back.
3. **Stop on dv, not on periapsis** — converged, or reversed (overshoot).

⛔ **Plus a backstop that does not trust the guidance at all:** if apoapsis ever exceeds 1.5× target,
the autopilot aborts and cuts the throttle, in every phase. An escape trajectory is the one failure
that loses the vehicle and the crew, so it gets a guard independent of whether the maths is right.

**And the burn is now instrumented at 0.5 Hz** (`ap / pe / circDv / thr`). The escape flight logged
nothing between CIRCULARISE and running dry, so the log could not say whether periapsis was even
rising — that gap is why this took a flight to find rather than a glance.

### THE SIMULATED SYSTEMS — `pure/VehicleSystems.cs`, built 2026-08-06 after the rule was corrected

**Sixteen buttons that logged "no KSP system behind this control" are now real controls on a simulated
system.** They were inert because I had read the simulate-don't-fake rule as covering gauges but not

Every event has a real trigger, read from the vessel:

| system | trigger |
|---|---|
| power strings trip | electric charge collapsed below 15%, shedding C then B then A |
| fire starts | a part above 90% of **its own** max temperature (skin or core, whichever is worse) |
| leak springs | measured g above 9 — the structure really is overstressed |
| consumables fall | the crew actually aboard, over the time that actually passed |

`POWER 1/2` shed a bus. `STRING 1A–2C` isolate. `RESET n` recovers tripped strings **and refuses while

not instantly. `SUPPRESS FIRE` is a one-shot bottle. `FIRE RESPONSE` is the procedure — shed bus 2 to
remove ignition sources, then discharge.

**an hour of quiet cruise raises no alarm at all** while the consumables still move; **a string the
crew isolated is never quietly re-closed**; and the model is **deterministic**, so three screens
rendering one instant agree exactly.

not because the control is broken.

row on the real capsule, so DEORBIT NOW / WATER DEORBIT / BREAKOUT arm and only fire on EXECUTE.

left and executing right must work. Two rules that cost nothing and matter: **EXECUTE with nothing

command switches rather than refusing.

### THE MAP: WHERE A PLANET'S SURFACE ACTUALLY COMES FROM — settled 2026-08-06

**There is not one loose planet colour map in this GameData tree.** Checked, not assumed: stock's
live inside KSP's own asset bundles and Parallax's inside
`Parallax_StockPlanetTextures/parallax-stock-planet-textures.unity3d`. The `.dds` paths in Parallax's
`_Configs` are BUNDLE asset names, not files you can open. **So the only way to get a planet's
surface is the live material, and that is not a compromise — it is the best copy that exists**: it is
literally what the player sees, it is already in VRAM, and it is automatically right under Parallax,
Kopernicus and RSS with nothing to keep in step and nothing to ship.

**Which slot, in order** (`ImageStore.MapSlots`):

    _ColorMap    Parallax Continued (shader Custom/ParallaxScaled)
    _MainTex     stock, Kopernicus, RSS
    mainTexture  last resort

⚠ **`_MainTex` EXISTS UNDER PARALLAX AND CONTAINS A 4×4 DUMMY.** The first version asked for
`_MainTex`, got a non-null texture, and logged `body map Kerbin 4x4` — a successful lookup returning
garbage. Hence the slot list *and* `MinMapPixels = 64`, which rejects placeholders. A null check
alone called that a success. When an unfamiliar shader turns up, the warning now names **every**
texture property on the material with its size, so the fix is adding one string to `MapSlots`.

**SCANsat is installed (21.1.0, KSPModStewards) and is NOT the base map.** It is a different thing:
altimetry / slope / biome, generated from PQS and **gated on the player having actually scanned the
body**, so a fresh save shows black. The Crew Dragon screen shows Earth as it looks, not as it has
been surveyed. It also has no documented public API for map textures and its licensing is stated only
in a `LICENSE.txt` that this install does not ship. It stays a possible *overlay* (terrain shading,
biome tint) behind a soft reflection check — never a dependency, never the base. Do not re-open this
without a reason that is not "we already have it installed".

### The globe, second pass — the square limb, 2026-08-06

First version drew each strip at its MIDDLE half-width, so every band was alternately narrower and
wider than the true circle and the limb came out as visible square steps.

**The fix is not "more strips".** Doubling them halves the step and never removes it. Instead each
strip now takes the half-width of its **equator-side edge**, so every band covers *at least* the
circle and overhangs by at most one strip height — then an annulus in the well's own colour
(`Inset2`) paints that fringe out. The disc is bounded by the annulus's INNER edge, which is an
`ArcGeometry` arc at 2°/segment. **Roundness is therefore independent of the strip count**; the strip
count only governs how smoothly the texture flows, which is why it went to 64. Deliberate asymmetry:
a strip that is too wide can be trimmed, one that is too narrow cannot be filled back in.

Also caught in the same screenshot: **the globe overflowed the panel on the launchpad.** The plot
scaled to the orbit's extents only, and on the ground that is the degenerate ellipse behind the
−598.4 km periapsis — apoapsis at the surface, periapsis at the planet's centre — so a very flat
ellipse blew the body up to 790 px inside a 520 px panel. Extents now take the max with the body
radius, and the ORBIT view **draws no ellipse at all when `ApogeeShown` is false**, saying
`ON SURFACE - NO ORBIT` instead. Same rule as the dashed apsides, same reason.

### NAVBALL + CREW SEATS — built 2026-08-06, from the triage above

**⚠ I WAS WRONG THAT `NavPage.Globe` IS A NAVBALL RENDERER.** It is not, and the reason matters: the
strip technique is exact only viewing a sphere from its EQUATOR — parallels are horizontal lines and
the pole is straight up. A navball turns about all three axes; under pitch the parallels become
ellipse arcs and roll tilts the whole grid. Neither survives axis-aligned quads, and an attitude
instrument that is geometrically approximate is an instrument that lies.

`src/NavBallRenderer.cs` does what MAS does: **a real sphere on a private layer with its own
orthographic camera**, rendered to a RenderTexture that the pages draw as `ImageId.NavBallLive`.
Every constant ported and cited, because this orientation maths looks plausible while being 90° out:

    layer 29                     MASPageNavBall.cs:56 - a layer KSP leaves free
    orthographic, aspect 1       :213-216;  model 2.4 ahead, far clip 13  :218, :232
    Euler(90,0,0) correction     MASVesselComputer.cs:635 - the vessel transform is rotated 90 about x
    MirrorXAxis + Euler(0,180,0) :611-614, :650 - MAS's own comment calls this voodoo. There is no
                                 reason to copy, only the result: it makes a rendered ball behave
                                 like the stock one.

The **sphere mesh is generated**, not shipped: a dozen lines beat a binary asset whose unwrap we
would have to trust, and it guarantees the UVs are equirectangular and match the texture.

**The crew card** replaces nothing and adds what the reference's A-Settings pages show: four seats,
occupancy from `part.internalModel.seats[i].crew` (per-SEAT, not a crew list — seat 2 empty is a
different fact from "3 aboard"; technique from `MASFlightComputer.cs:1694-1716`). One asset, three
readings, by tint: crewed / empty / no such seat.

**Touching a seat moves the IVA view to that crew member** (`CameraManager.SetCameraIVA`). That is
the deliberate answer to the reference putting per-seat AUDIO there: stock KSP has no cabin audio, and
this project simulates a *reading* but never a *control*. A volume slider bound to nothing would have
been the one thing the rules forbid, so the seat does something the game really can do.

`SeatPart` prefers **the part carrying `DragonScreenState`** — our own module is the marker for "this
is our capsule", which matters on a docked stack where the station has crewed parts too. A first
attempt used `InternalCamera.currentPart`; that property does not exist and the compiler caught it
(trigger #3), and it was the wrong question anyway — the card describes the capsule the displays are
IN, which does not change when the player looks elsewhere.

**Preview:** `NavBallLive` gets its OWN stand-in — its own skin, clipped to a circle. Sharing the
body-map stand-in would have drawn **Earth as the attitude ball**, which is worse than drawing
nothing because it looks deliberate. What the preview cannot show is orientation; that needs a camera
and is a question for the game.

### ⚠ STATICS THAT OUTLIVE A SCENE MUST VALIDATE, NOT REMEMBER — found in flight 2026-08-06

**Symptom:** revert to the VAB, launch again, and the NAV map and the navball are both gone. The
pages, the rings and the file-loaded art all still drew, which is what made it look like an art
problem rather than a lifetime one.

**Cause, and it is one cause with two faces.** A scene load destroys GameObjects but NOT textures,
materials or meshes — those are assets and merely leak. So:

- `NavBallRenderer` kept `tried = true` and a non-null `target` while its `ballObject` and
  `camObject` had been destroyed with the scene. It went on handing out a RenderTexture nothing was
  rendering into. **A blank texture, served confidently** — the same class of failure as the 4×4 body
  map, one level up.
- `ImageStore.BodyMap` keyed its cache on the CelestialBody. Kerbin is the same object across a
  scene change, so the check passed while the texture it had cached was gone.

**The rule:** a static that survives a scene must re-check its Unity objects, never trust a flag
about them. `== null` is true for a destroyed object and costs nothing to ask. All three caches
(navball, body map, `ImageStore.Get`) now validate and rebuild; the DLL-only fix needs no cfg change.

**This also generalises the earlier lesson.** "A negative result must be cacheable" (UI trap #3) had
a mirror nobody wrote down: *a positive result must be re-validated.*

### Attitude ball orientation — SOLVED 2026-08-06, and the hypothesis here was WRONG

This section used to blame MAS's `MirrorXAxis` + `Euler(0,180,0)`, on the theory that it was tuned
against MAS's navball *model* while ours is generated. **That was wrong and it is worth keeping the
correction visible: the quaternion ports fine, the TEXTURE is stored transposed.** Full write-up at
"THE NAVBALL WAS TRANSPOSED, NOT ROTATED" near the top; the tool is
`plugin/build/navball_preview.py`.

The instrumentation is what made it cheap — refusing to guess was right even though the hypothesis
behind the instrument was not. `Orient()` still logs, but **three lines then quiet**, as a
per-load confirmation rather than a running diagnosis.

Also fixed: the ball's diameter is now DERIVED from the ALIGN ring it sits inside
(`Pages.BallDiameter`), not a hand-picked 0.52 of the ring height that left ~10 px and touched it in
game. The test asserts the CLEARANCE and that the ball is concentric, so the two cannot be edited
apart.

### PROPELLANT FOLLOWS THE ENGINES THAT ARE BURNING — fixed 2026-08-06, found in flight

**Symptom:** the dial read 100% the whole way to orbit. **Nothing was broken** — it was reading
`MonoPropellant`, the Dracos, which are untouched during ascent. A correct number answering a
question nobody asked, which is the same family as orbital speed on the launchpad and the third
member of it.

`VesselData.Propellants()` now collects what the **lit** engines consume
(`ModuleEngines.GetConsumedResources()`, per `MASVesselComputerModules.cs:530`), falling back to
every engine still attached when nothing is burning — so the pad and a coast show the stage about to
be burned, and once the booster separates its engines are on another vessel and the set narrows by
itself. No staging logic needed.

Three decisions worth keeping:

- **The MINIMUM fraction, never the average.** A bipropellant stage is finished when the *first*
  propellant runs out; averaging would read 50% at the instant the oxidiser hit zero and the engines
  died.
- **Massless resources are not propellant** (`density <= 0`) — ElectricCharge and IntakeAir come back
  from `GetConsumedResources` for ion and jet engines.
- **`SolidFuel` is NO_FLOW**, so the crossfeed-respecting query legitimately reports nothing at
  vessel scope. `ResourceById` retries with `pulling=false` rather than showing a thrusting booster
  as empty.

**And the caption names the source** — `PROPELLANT LF/OX`, then `PROPELLANT MONOPROP`. This dial now
means different things at different times, and the velocity readout already paid for that lesson: a
number that silently changes meaning is worse than one that is consistently wrong, because nothing
on the screen says it changed.

### Renderer: IMGUI + `GL`, not uGUI

Settled 2026-08-05 **by evidence, after I recommended uGUI and was wrong.**

- **MechJeb2 is IMGUI everywhere** — 52 files using `OnGUI`/`GUILayout`; the single
  `UnityEngine.UI` reference is `InstallChecker.cs`, a startup dialog. Every window, button, the ascent
  guidance and maneuver planner. Source on disk at `Desktop/mechjeb_src`.
- **MechJeb draws vectors with `GL`** — `MechJeb2/GLUtils.cs`: `GL.PushMatrix`,
  `GL.Begin(GL.TRIANGLES)`, `GL.Begin(GL.LINES)`. Procedural, in C#, no editor.
- **uGUI in KSP means the Unity Editor.** The tell is separate assemblies — `SCANsat.Unity.dll`,
  `RocketSoundEnhancement.Unity.dll`. Build prefabs in Unity 2019.4.18f1, export an AssetBundle, load
  at runtime. A whole new toolchain, and it makes iteration **worse** than the DLL rebuild we have.
- A DLL merely *referencing* `UnityEngine.UI` proves nothing (MechJeb2.dll appears in that scan and is
  IMGUI throughout). **Do not repeat that weak test.**

### ⚠ The render-path catch

**`GUI.*` (IMGUI) draws to the SCREEN and CANNOT target a RenderTexture.** So:

    page CONTENT   ->  Graphics.DrawTexture + GL.Begin(GL.TRIANGLES/LINES) into a RenderTexture
    chrome + input ->  IMGUI

Get this backwards and you build a page that can never leave the floating window. The floating window
is a **development view** of the same RenderTexture — iterate without sitting in IVA — not the product.

### ONE SCREEN, FOUR SURFACES — settled 2026-08-05, user's call

**All three IVA screens are identical in capability. The user chooses which page each one shows.**
That is what the real capsule does — the displays are general-purpose and crew-selectable, which is
exactly why no public source documents a page-per-screen assignment (`docs/REAL_DRAGON_SCREENS.md`).

**MAS arrived at the same design independently, which is the evidence this is right.** Every
`MASMonitor` is the same class with the same page set; the page it currently shows is a persistent
value keyed by `monitorID` (`MASMonitor.cs:269-278`), and that value lives in a store on
`MASFlightComputer`, which is a **`PartModule`** on the pod (`MASFlightComputer.cs:44`).

    ONE page set + ONE renderer + ONE nav bar
        -> IVA screen 1 (left)     surface: TT_CD2_IVA_SCREEN1
        -> IVA screen 2 (centre)   surface: TT_CD2_IVA_SCREEN2
        -> IVA screen 3 (right)    surface: TT_CD2_IVA_SCREEN3
        -> out-of-vehicle UI       surface: an IMGUI window drawing the same RenderTexture

The out-of-vehicle UI follows the **single-screen, five-page** shape of
`assets/reference/dragon2-ui-vue` — one page at a time with the page selector along the bottom.
It is not a separate program: it is a fourth instance whose surface happens to be a window instead
of a prop material, which is why it costs almost nothing and why it can never drift out of step with
what is on the glass. This is also what brings ClickThroughBlocker back into the build.

**THE CONSEQUENCE THAT MUST NOT BE DESIGNED AROUND LATER: the selected page cannot live in the
`InternalModule`.** Internal models are torn down and rebuilt, so a page selection stored there is
lost on the next rebuild, and lost again on every save/load. It belongs on a **`PartModule` on the
pod**, one persistent value per screen id — the MAS arrangement above, and the reason MAS has a
`PartModule` at all when everything visible is an `InternalModule`.

Corollary: `screenIndex` in the cfg stops being a role and becomes an **identity** — the key the
page selection is stored under. Nothing about a screen's behaviour may branch on it.

**The page set and the starting selection** (full reasoning in `docs/REAL_DRAGON_SCREENS.md`):

    FLIGHT   telemetry strip + Dragon illustration + Earth      -> screen 2, CENTRE
    VEHICLE  subsystems, consumables, alerts, dial gauges       -> screen 1, LEFT
    NAV      trajectory, ground track, orbit                    -> screen 3, RIGHT
    DOCKING  approach and docking controls
    SETTINGS cabin, audio, lighting, cameras

Already in the cfg as `defaultPage`, logged at startup, wired to nothing until the router exists.

the software decided it knew better.

### Where the cfg line is — the ONE-SENTENCE TEST

The rejected thing was a **cfg-driven page engine**, not cfg. `DragonScreen.cfg` is necessary and
correct; there is no way to attach an `InternalModule` to a prop without it.

    THE TEST:  could someone add or change a PAGE by editing a text file, without rebuilding the DLL?
               YES -> that is the engine. Stop.
               NO  -> it is wiring. Fine.

| fine — this is wiring | the drift — stop me |
|---|---|
| which transform, which screen id | `PAGE { ELEMENT { type = arc … } }` |
| render width, MSAA, default page name | element types, positions or colours in config |
| debug flags like `dumpTransforms` | variable names as strings, resolved at runtime |
| a fixed, small set of typed fields | a generic interpreter that walks config nodes |

**Why, so the rule can be applied rather than obeyed:** a page engine moves the page out of compiled,
typed, headless-testable C# and into an untyped format with no compiler and no tests — straight into
the layer this project already knows is where the bugs live. It is a large up-front cost that only
pays off if *third parties* author pages, which nobody has asked for. And **MAS already is that
engine**; if data-driven pages were the goal, the right move would be to use MAS, not to rebuild it
worse. Every argument for building it is an argument for not building this mod.

**The borderline case, named in advance:** the preview harness needs a display list that both the GL
painter and the PNG previewer read. That is fine *while it is an in-memory structure emitted by C#
page code*. The moment it wants to be serialised to a file that someone authors, it has become the
engine — and that is the drift to catch.

### SIMULATE, DO NOT FAKE — and do not refuse either. Settled 2026-08-05, user's call

> "we should 'fake' things like ppo2 cabin temp cabin pressure etc. It would look more realistic if
> they acted as if they were functioning rather than no display or reading all zero."

I had left the life-support dials off the VEHICLE page because stock KSP models none of them. That
was the wrong end of the trade — **a blank panel is less honest-looking than a working one, and far
less useful.** The right distinction is not real-versus-invented, it is:

| | |
|---|---|
| **FAKE — never** | a constant, or a random number. Indistinguishable from a dead sensor, which is what the no-invented-telemetry rule exists to prevent. |
| **SIMULATED — do this** | derived from real state by a stated model. Moves because the vessel moved. That is what this whole mod is. |

`src/pure/CabinEnvironment.cs` computes PPO2, CO2, cabin pressure, cabin temperature and both coolant
loops from inputs that ARE real: **crew count, hull temperature, and the electrical state.** So the
cabin warms during entry because KSP really is heating the hull, CO2 climbs with four aboard, and
losing power **degrades** the readings instead of freezing them — a fake cannot fail convincingly, a
model can. It is deterministic, so three screens showing one instant agree exactly.

**The rule that keeps it honest: every value must MOVE, and move BECAUSE OF SOMETHING.** If a reading
cannot be tied to a real input or a stated model, it does not go on the glass.

#### ⚠ AND IT APPLIES TO SYSTEMS AND CONTROLS, NOT JUST GAUGES — extended 2026-08-06, user's call

> "it is ok to simulate features that ksp does not actually have, it is not a lie it is a falcon 9
> crew dragon simulation"

I had been reading the rule far too narrowly: happy to simulate a *reading*, but refusing to simulate
a *system*. So the power strings and the cabin emergencies got wired to log lines saying "no KSP
system behind this control", and the MECH pressure group was left showing cabin gas under tank names.
**That was the same mistake as the blank life-support panel, made a second time.**

This is a Falcon 9 / Crew Dragon **simulator**. Simulating a redundant power-string architecture, a
cabin fire, or a depressurisation is not dishonest — it is the entire point. The line is unchanged
and it is still the only line:

- **Derived from real state by a stated model** → build it. A fire that starts because a part really
  is at 92% of its maximum temperature is simulated. A string that trips because electric charge
  really collapsed is simulated.
- **A constant or a random number** → still never. That is the thing a dead sensor is
  indistinguishable from.

So: **do not refuse to build a control because stock KSP lacks the system.** Model the system from
real inputs, then wire the control to the model. The only controls left inert are ones where no
honest input exists at all — and that list should be checked before it is believed.

### Static art vs live elements

A static faceplate with every *moving* element drawn as real geometry bound to real values is how glass
cockpits actually work, and is fine. What is **not** fine, and was explicitly ruled out: pre-rendered
images *as the mechanism* — image-swapping per phase, hotspots over a bitmap, more pre-rendered pages.
Nothing on a flat image can ever update.

## Build

**Roslyn from the installed .NET SDK, via a response file. Still no IDE, no MSBuild, no NuGet.**

⛔ **THE LANGUAGE VERSION AND THE RUNTIME TARGET ARE TWO KNOBS — 2026-08-12.** This said
`csc.exe at C:\Windows\Microsoft.NET\Framework64\v4.0.30319\`, the 2012 compiler Windows ships,
which caps at **C# 5** — and the project treated that as a KSP requirement for months. It never was.
Modern C# (`$"..."`, `?.`, `=>` members, pattern matching) is compile-time sugar that lowers to
ordinary IL, and KSP's Unity 2019.4 Mono runs it. MechJeb ships modern C# into this same game.

`build.py` now finds the newest Roslyn under `C:\Program Files\dotnet\sdk\*\Roslyn\bincore\`
and compiles with `-langversion:latest -deterministic -nostdlib`, naming **KSP's own**
mscorlib/System/System.Core (never the SDK's .NET 10 refs — those compile and then fail to load).
**It falls back to the Framework compiler when no SDK is present**, so a bare machine still builds;
it just cannot accept modern syntax and labels the build `[C#5 fallback]`.

Two consequences worth knowing:

- **All three targets moved together, deliberately.** The tests compile `src/pure` too, so leaving
  them on the old compiler would have pinned `src/pure` to C# 5 — which is exactly where the
  MechJebLib port lands. Verified by compiling a probe with C#6/7 syntax through both.
- **Builds are deterministic now.** Two builds of unchanged sources give a byte-identical DLL.
  `_same()`'s comment says this is impossible; that was true of the legacy compiler, not Roslyn.

⚠ **UNPROVEN UNTIL THE NEXT LOAD:** a Roslyn-built DLL has compiled but has never been run by
KSP. If the game rejects it, the fallback is one constant.

    python plugin/build.py          build the DLL
    python plugin/build.py test     build + run headless tests (game closed)
    python plugin/build.py preview  render the pages to build/preview/*.png (game closed)
    python plugin/build.py install  copy GameData/<mod> into the KSP install

### RESTARTS ARE THE SCARCE RESOURCE — spend them deliberately

A DLL change needs a full restart. **So does a cfg change** — ModuleManager applies patches at load,
and there is no in-flight reload worth trusting. So the only levers are batching and moving work out
of the game:

1. **Batch.** Never one change per load. Queue everything worth testing, build once, restart once.
2. **`preview` renders the real pages to PNG with the game closed** — same `DisplayList`, same
   `ProofPage`, same `ArcGeometry`, at the measured 1280x703 / 1280x710. Layout, proportion, palette
   and legibility are settled here in seconds. It does NOT promise pixel-identical output: GDI+ and
   the GPU anti-alias differently, and the real screen is a texture on angled geometry under
   Deferred.
3. **`captureOnLoad = true` writes each render target to
   `<KSP>/DragonScreen_capture/screenN.png`** shortly after it goes live, and `captureKey` captures
   on demand for the frames that only happen during a burn or an approach. This is **strictly better
   evidence than a photograph of the cabin**: pixel-exact, no perspective, no cabin lighting, no
   cropping, and no work for the user beyond loading in.
4. **Spend a restart only on what needs the capsule**: material behaviour, legibility at IVA
   distance, input — and how it actually looks on angled glass, which nothing else can show.

**The four evidence channels, cheapest first.** Reach for them in this order:

| channel | answers | cost |
|---|---|---|
| `KSP.log` | sizes, aspects, shaders, transform dumps, errors — anything numeric or structural | ~nothing |
| `build.py preview` | layout, proportion, palette, legibility | no game at all |
| `captureOnLoad` PNG | what the screen ACTUALLY drew, pixel-exact | one load, no user effort |
| a screenshot | how it looks in the cabin: lighting, angle, distance, surrounding art | user effort |

Screenshots are not obsolete — the button close-ups that produced the whole console transcription
could not have come from anywhere else. They are just the wrong tool for the first three rows.

**The two renderers must never disagree**, or the preview is worse than useless. Anything that
decides geometry lives in `src/pure` where both call it — notably `ArcGeometry.ArcScreen`, which owns
the y-flip. Neither renderer is allowed its own copy of a sign.

**Build here, copy to GameData only to test.** The user plays this install.

**IT IS NOT ALWAYS KSP HOLDING THE DLL.** Caught 2026-08-05 with the game closed: **CKAN**
(`ckan-windows`) keeps the GameData tree open and a copy fails with `WinError 1224`. Close both.
`install` copies the **DLL first** for this reason — a lock then leaves the install untouched and
self-consistent, instead of writing a new cfg against an old DLL, which looks installed and is not.
There is no reliable pre-test for a Windows file lock; the old guard opened the destination in
append mode, which succeeds on a mapped DLL, so it never fired.

**UnityEngine is SPLIT INTO MODULES in 2019.4** and the split is not intuitive; `CS0012` names the
assembly it wants. Already encoded in `build.py`:

    CoreModule             MonoBehaviour, Texture2D, Rect, Color, Debug
    IMGUIModule            GUI, GUILayout, GUIStyle
    TextRenderingModule    TextAnchor, Font   (GUIStyle.alignment lives here)
    ImageConversionModule  Texture2D.LoadImage / EncodeToPNG  (EXTENSION methods)

**No ClickThroughBlocker dependency right now** — `EXTRA_REFS` is empty because nothing draws an IMGUI
window yet. It returns with the out-of-vehicle window; namespace `ClickThroughFix`, class

## UI traps already paid for — read before writing UI code

1. **`GUILayoutWindow` renders a 0x0 window** if the draw function emits no GUILayout content. It
   auto-sizes from content. Use `GUIWindow` for absolute layout. No error, clean log, invisible panel.
2. **NEVER allocate inside `OnGUI`** — it runs at least twice per frame (Layout, then Repaint). Caught
   three times: swatch textures, then a `GUIStyle` cloned to recolour one word. Build one style/texture
   per STATE up front; never mutate or clone in the draw path.
3. **A negative lookup result must be cacheable.** Keying a re-search off `thing == null` re-scans the
   whole part list every call on every vessel that lacks it. Use a separate `searched` flag.
4. **Hairlines need pixel snapping.** A 2 px stroke scaled to a 960 px panel is 0.56 px — a grey smear.
   Positions scale; stroke widths snap to whole pixels with a floor of 1.
5. **Two views sharing a surface must be EXCLUSIVE, not layered**, or debug furniture draws over art.
6. **kOS writes rich text** (`<b><color=red>ABORT</color></b>`). Any style rendering such a string needs
   `richText = true` or the pilot reads tags instead of words.

## How to work on this project

These are the user's standing rules, and they cost real money when broken.

1. **Check whether it already exists before building it.** Assets, fonts, libraries, mods, algorithms.
   Then **verify what you found actually matches** before adopting it — "free and available" is not
   "suitable". State what you searched for and what you found, with links, before downloading.
2. **Look before you reason.** For any concrete question, the first action is a targeted Read/Grep, not
   a paragraph of theory. The code and the files are ground truth.
3. **Decide once.** No "wait… actually…". Design the whole change set before the first edit; re-opening
   your own edit is the same waste as re-opening a decision, it just looks like progress.
4. **Take the user's clues literally and first.** On this project they have been right more often than
   I have — including "doesn't MechJeb use an interactive UI built in C#", which reversed a decision
   I had recommended.
5. **Terse chat.** Root cause, fix, one caveat if it matters.
6. **Quarantine before deleting.** `Desktop/quarantine/`.

**Do not silently change the agreed architecture.** On 2026-08-05 I drifted three times in one session
— a cfg-driven page engine, hand-rolling geometry that was already downloaded, and uGUI — and the user
caught all three. If something looks like it needs a different approach, say so and get agreement
first.

### The render path — FLOWN AND PROVEN, 2026-08-05

Three live screens in the capsule on the first try. What the proof pattern settled, from screenshots:

- **The mechanism works.** RenderTexture → `_MainTex` on the prop material, drawn with `GL`.
- **It is live** — the arc moved between two shots.
- **UV orientation needs no flip.** Red landed top-left and green bottom-right on all three, i.e.
  `GL.LoadPixelMatrix(0, w, h, 0)` top-left origin maps straight onto the glass.
- **The addressing**, which is what makes per-screen page assignment possible at all:

      TT_CD2_IVA_SCREEN1  ->  LEFT      TT_CD2_IVA_SCREEN2  ->  CENTRE      TT_CD2_IVA_SCREEN3  ->  RIGHT

- **One defect, found exactly as intended: the aspect was wrong**, and the fix is CONFIRMED in game.
  1024x640 was the Figma reference aspect (1.62:1) and the circle came out an ellipse. Fixed by
  MEASURING — `ScreenLayout.AspectFromExtents` reads the mesh bounding box, `PixelHeightFor` derives
  the height, `screenWidth` is the only resolution knob and the cfg carries no height.

      screen 1  0.2844 x 0.1561   aspect 1.8219   ->  1280x703
      screen 2  0.2816 x 0.1561   aspect 1.8038   ->  1280x710     <- 1% NARROWER
      screen 3  0.2844 x 0.1561   aspect 1.8219   ->  1280x703

  **1.82:1 — neither the 1.62 I first used nor the 2:1 I then estimated.** And the CENTRE SCREEN IS
  NOT THE SAME SHAPE as the outer two. Never assume the three are pixel-identical.

  Consequence for page design, and it is not small: **the reference art does not fit the screen.**
  A page composed to the 1.62:1 Figma frame will letterbox. Compose to the measured shape; the art is
  a source of proportions, colours and technique, not a frame to fill.

- **The material is `KSP/Unlit` on per-screen materials `TE_CD2_SCREEN_1/2/3`** — not the shared
  `TE_CD2_PROP_SCREENS_TXT` / `KSP/Diffuse` that `docs/IVA_TARGET.md` claimed from reading `.mu`
  strings. Unlit means the displays are self-lit and do not dim with the cabin, which is correct and
  free. **`.mu` strings name assets, not live material state** — read the running game.

- `Hidden/Internal-Colored` resolved on all three screens; no shader fallback needed.

- **The arc was aliased, and the render target now runs MSAA x4.** Measured off the close-ups rather
  than guessed: the stair-steps are exactly ONE render-target pixel.

  **DO NOT "FIX" THE TESSELLATION.** At 2°/segment and r = 150 px the arc's sagitta is **0.02 px** —
  the chords are three orders of magnitude finer than the error being seen. Subdividing would cost
  vertices every frame on three screens and change nothing. This design is arcs and hairlines and
  almost nothing else, so anti-aliasing is not polish; it is most of whether it looks right.

### The render path — as built

    plugin/src/DragonScreenMonitor.cs   InternalModule: RenderTexture -> prop material _MainTex
    plugin/src/ScreenPainter.cs         GL immediate mode into that RenderTexture
    plugin/GameData/DragonScreen/DragonScreen.cfg   three MODULEs on @PROP[TE_CD2_IVA_SCREEN]

Shape ported from `MASMonitor.cs:212-222`, not invented. A `Camera` with `targetTexture` set and
`cullingMask = 0` exists solely to give `OnPostRender` a legal place to run GL with the RenderTexture
already bound — that is why there is a camera that shows nothing.

**Coordinates are top-left origin, pixels** (`GL.LoadPixelMatrix(0, w, h, 0)`), which mirrors triangle
winding, which is why the GL material forces `_Cull Off`. Without it a flipped Y culls every filled
shape and leaves a black screen with no error.

The proof pattern is scaffolding. Each element answers exactly one question in one game start:
anything at all = the texture reaches the material; a sweeping arc = it is live; red top-left vs green
bottom-right = mesh UV orientation; circle inscribed in square = whether 1024x640 matches the physical
aspect; N bars = which transform is which display. **Delete it when a real page draws.**

### TEXT — SETTLED 2026-08-05 by reading MAS, and it was simpler than either candidate

**Neither guess was right.** MAS does *not* use `TextMesh` components. `MdVTextMesh` (itself derived
from RPM's `JSITextMesh`) builds **its own quad per glyph**:

    font.RequestCharactersInTexture(ch, size)   MdVTextMesh.cs:667-679
    font.GetCharacterInfo(ch, out info, size)   -> uvTopLeft..uvBottomRight, minX/maxX/minY/maxY, advance
    -> vertices + uvs                            MdVTextMesh.cs:938-962

MAS writes those into a `Mesh`; **we feed the identical numbers straight to `GL`**. So there is no
`TextMesh` GameObject, no private culling layer, no AssetBundle, and **no atlas generator to write** —
Unity builds the atlas and the glyph metrics come with it.

Two traps this creates, both handled and both worth knowing:

1. **Request every glyph BEFORE reading any UV.** Requesting can *rebuild* the atlas, which
   invalidates every UV already read. Interleaving request and draw is the classic dynamic-font
   corruption bug. `RequestGlyphs()` runs over the whole page first.
2. **Text needs a different material from shapes**, so `Execute` switches `SetPass` as it walks. It
   walks **in list order** — sorting into "shapes then text" would batch better and would silently
   break every page with a label on a panel, which is most of them. Painter's algorithm; last drawn
   wins. The atlas texture is re-assigned on each switch because a rebuilt atlas is a *new texture*
   and a material pointing at the old one draws blanks.

**Fonts: `CreateDynamicFontFromOSFont` only sees fonts INSTALLED IN WINDOWS.** D-DIN is bundled under
the OFL in `assets/d-din` but is **not installed**, and an uninstalled name *silently substitutes*
rather than failing — so `fontName` is a cfg field and the painter logs what it actually resolved.
`PreviewMain.FontFamily` must be changed with it, or the preview flatters us with typography the game
cannot produce. (System.Drawing's `PrivateFontCollection` *could* load the TTF directly and is
deliberately not used, for exactly that reason.)

**For release this is not good enough** — a mod cannot ask users to install a font by hand. The route
is MAS's other path: a bitmap font from a texture plus `CharacterInfo` (`MASLoader.cs:376-474`), no
OS install and no AssetBundle. Not built yet because it is not needed yet.

**Layout limit, stated now:** measuring a string needs a font, which `src/pure` refuses to have. So a
page can *anchor* text (left/centre/right of a point) but cannot lay out relative to how wide another
string turned out. When that is needed the answer is a **measurement interface the two renderers
implement** — not a font inside `src/pure`.

**And the allocation rule reaches text:** `"ALT " + v.ToString("F1")` allocates a string every frame
on three screens. Pages must cache formatted text and rebuild only when the value changes. The proof
page's caption is built once in `Configure` for exactly this reason.

## Typography — 16 px is MEASURED, and it changes how hierarchy works

Established in game 2026-08-05 from the proof page's legibility ramp, at 1280 px across a 0.2844 m
screen, from the seat:

> "technically every single one is visible from the seat as you can use the mouse wheel to zoom view.
> **16px is legible without needing to zoom**"

Both halves matter. **Zoom means nothing is unreadable, so there is no hard floor** — but text the
pilot has to zoom for is text they will not read during an approach. The threshold that counts is
GLANCEABLE, and it is 16.

    Typography.Min = Caption = 16    the glanceable floor. Values, alerts, chrome, anything live.
              Body           = 20
              Value          = 28
              Hero           = 40    once per page, or it stops meaning anything
              Dense          = 12    BELOW the floor. Reference tables you lean in for. Never live.

**THE RULE: never shrink below 16 px to create hierarchy — go dimmer instead.** That is not a
compromise, it is what the source art already does. `DragonPalette`'s nine-step ladder exists, in its
own words, to carry "the hierarchy that would otherwise need weight or size changes". Caption-versus-
value on this design is a brightness difference far more than a size one.

## The chrome bar — built 2026-08-05, `src/pure/ChromeBar.cs`

The global nav bar: page links · vehicle STATE · comms link + timer · MET, drawn over every page on
every screen, because the research says build the chrome before any page.

**The alert routing is the point.** A page link turns alarm-coloured when that page holds a
non-nominal condition, so any screen says "the problem is over there" and is one touch from it.
**Alert beats selected** — a selected page that is also in alarm must read as ALARM, or the highlight
hides the one thing the bar exists to show. Pinned by a headless test.

That test earned its keep immediately: it failed on the first run because the readout caption said
**VEHICLE**, which is *also a page link* 500 px away on the same bar. The test picked the wrong one —
and so would a pilot. Renamed to **STATE**, which is both unambiguous and more accurate for a value
reading NOMINAL. **A duplicated word on one bar is a real defect, not a naming quibble.**

### ⚠ TECHNICALLY CORRECT IS NOT THE SAME AS USEFUL

Shipped a FLIGHT page reading **175 m/s standing still on the launchpad**. Nothing was broken:
`Vessel.obt_speed` is orbital speed and Kerbin rotates at 175 m/s. The same audit found **periapsis
−598.4 km** on the ground — also true, because a landed vessel's "orbit" is a degenerate ellipse
through the planet.

Both are correct numbers that make the screen look broken. **Before displaying a value, ask what it
reads as in EVERY regime the vehicle passes through** — on the pad, in atmosphere, in orbit, docked.

The fixes, and the shape to copy:

- **Velocity follows the regime AND the caption names it** — `SURFACE VELOCITY` / `ORBITAL VELOCITY`.
  Changing the number without changing the caption would be its own trap: a speed that silently
  switches meaning is worse than one that is always wrong the same way.
- **Apoapsis/periapsis dash out on the ground, but NOT in atmosphere** — an ascending rocket's
  apoapsis is precisely what the pilot is watching.
- KSP's eight `Vessel.Situations` collapse in the glue to three display regimes; the **policy** —
  which speed, which fields are meaningful — is in `src/pure`, headless tested. The
  `LANDED | PRELAUNCH | SPLASHED` grouping was checked against MAS (`MASAutoPilot.cs:257`), not
  invented.

Nine tests pin this exact bug: on the ground the page must show surface speed, must **not** show the
175, must name which velocity it is, and must not print a periapsis inside the planet.
