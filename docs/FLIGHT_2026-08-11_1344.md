## F1 · "no free docking port on the station" was a false statement

`OpenPorts` scans `station.parts`. **An unloaded vessel has no parts** — KSP holds it as a
ProtoVessel past the load distance, so the list is empty and every port scan returns zero. We were
10.2 km out; KSP's default orbital load distance is far inside that.

The partdump settles what was actually there at that moment: **21 docking nodes, only 2 docked, 12
of them `KDSS-P Docking port for stations (passive)`** — the exact mate for the Dragon's
`KDSS-A ... (active)`. Both are `nodeType = KDSS` (`KDSS/Parts/KDSS/KDSSA.cfg:42`, `KDSSP.cfg:43`),
so `PickPorts`'s type match would have paired them. There was never a shortage of ports.

F9I never had this fault because it raises the ranges on the **target** and waits:

```
station_ops.ks:1147   set target:loaddistance:orbit:unload to 25000.
                      set target:loaddistance:orbit:load   to 10050.
                      set target:loaddistance:orbit:unpack to  2100.
                      set target:loaddistance:orbit:pack   to  2250.
station_ops.ks:1153   until target:loaded or time:seconds > stLoadT ...
StClosestPort:150     if not target:loaded { "target not loaded - cannot read its ports yet" }
```

Ported verbatim into `DockingOps`: a new `DockStage.AwaitingTarget`, `RaiseTargetRange`, and a 30 s
`AwaitTarget` wait. `load` is 10050 m — fifty metres outside the direct-approach gate, so the
station is in memory *before* the approach hands over. The timeout refuses with the real reason and
the real distance.

## F2 · The docking approach had no roll reference

`FlyTo` steered `SteerTo(ship, -axis, Vector3d.zero)` — roll unconstrained. Both halves of the pair
carry `captureMinRollDot = 0.5`, so the ports must be within 60° of roll or **the magnets never
latch however perfect the approach was**. Now referenced to the target port's own `up`.

Same omission as the booster flip's missing roll reference on the 13:34 flight.

## F3 · The 300 s burn backstop was being measured from before a 3663 s warp

`st.ElapsedS = now - startedAt`, and `startedAt` is stamped when the **phase-down settles** — before
`FindPass`, before the wait for the pass, and before the warp to it. On this flight the warp alone
was 3663 s, so the backstop had expired 3388 s before the engine lit: ignition 13:52:07.241,
"complete" 13:52:07.260, **19 milliseconds of thrust**, reported as a runaway.

New `ignitedAt`, stamped at ignition, feeds `ElapsedS`. The 30 s alignment timeout got the same
treatment via `aligningSinceAt` — it was reading true the instant the warp ended.

## F4 · No propellant floor on the Dracos

`DeorbitBurn.Complete` already stops on `UsingS2 && S2FuelUnits < S2FuelFloorUnits`. There was **no
equivalent for monopropellant**, which is what the Dracos actually burn. So the phase-down held the
throttle open for 301 s against a dry tank and blamed the backstop. Added `MonoFloorUnits = 5.0`
and `ABORTED - out of monopropellant`, same figure and same reason as the S2 floor.

Tests: the de-orbit fixtures were leaving `MonoUnits` at zero, so two of them started failing the
moment the floor existed — a fixture at zero *is* an empty tank. Fixed the fixture, and added three
checks including "an S2 de-orbit does not care that the mono tank is empty".

## F5 · Short of the reserve and short of the burn are different failures

The budget said `have 18.9, need 143.6 ... margin -124.7` and then flew. Missing the entry/landing
reserve still gets the capsule into the atmosphere where it has chutes; **not being able to finish
the de-orbit burn leaves it in orbit with an empty tank and no options at all.** The second is now a
refusal naming both numbers; the first stays a warning.

Capacity confirmed from the partdump: `MonoPropellant: 195 / 195`. 18.9 was genuinely what was left.

## F6 · A failed de-orbit was handed to the entry sequence

Periapsis 80.1 km is **ten kilometres above the atmosphere** — a stable orbit. `EntryOps.Engage` ran
anyway, jettisoned the trunk, and then had nothing to do for 22 minutes. The gate is now physical
(`PeriapsisM > mainBody.atmosphereDepth`) rather than a reading of the abort string, because what
matters is where periapsis ended up, however the burn ended.

## F7 · The trunk jettison, and a diagnostic that pointed at the wrong thing

`trunk jettison commanded (0 decoupler(s))` — a jettison that never happened, logged at LOG level as
though it had. Then, 1.5 s later, `TRUNK WILL NOT JETTISON - entry attitude cannot be held`, which
sent debugging at the steering. **The steering was holding 0° off retrograde perfectly.**

The partdump corrected my first diagnosis. The trunk offers **both**:

```
MODULE: ModuleTundraDecoupler
   events : [decouple]
   actions: [decouple]
```

so the name matched and the part was in `DockedSide.Ours` — `HasPart` found it with the same list
one line earlier. The only filter between the two is `ev.active`, which `DoEvent` skipped in
silence. That skip is now counted and reported.

And `DoEvent` now falls through to the **action**, which is a port, not a guess: F9I never used
events for this at all — `dragon_deorbit.ks:892` is
`DgDoAction(dgTRUNK, "ModuleTundraDecoupler", "decouple")`. An action carries no `active` flag,
which is exactly why the proven path never hit this.

`n == 0` is now an error in its own right, at the moment it happens.

## Recorded, not fixed

1. **Nothing closes a gap wider than 10 km.** The capsule was at 10.2 km **receding at 116 m/s** and
   the only honest answer available was STOPPED. That is by design — F9I deleted its phasing after
   flight 011 and the audit's research confirmed deletion over rewrite — but it means the profile
   depends entirely on arriving inside the gate. On this flight it could not: the save began in a
   182 × 81 km orbit left by the 13:34 runaway approach, whose sign bug is now fixed. **Re-measure
   the arrival on a clean ascent before treating this as a hole.**
2. `ReturnBudget.MonoIsp = 184.0` vs the 305 s in `falcon-dragon-two-decouplers`. 184 is F9I's own
   `stMonoIsp` (`station_ops.ks:260`) and the port is faithful to the flown value. Left alone.
   Do not "correct" it from the part config.
3. `DockingOps.FlyTo` still re-derives closing rate by hand (`Dot(-relVel, to)`) instead of using
   `RelativeMotion`. The sign is **right** — checked — but it is the third copy of the definition
   that `RelativeMotion` exists to remove, and it works on port positions rather than CoM so it
   needs an overload.

# Second pass — what the LOG did not show

I answered "did you find all the issues" with the above, and the honest answer was **no**. The first
pass read the tagged lines out of `KSP.log`. It never opened the flight recorder, and
[CLAUDE.md](../CLAUDE.md) is explicit that the recorder is the primary instrument and `KSP.log` is
not. It also never checked for exceptions that carry no `[DragonScreen]` tag.

Both done now. `flight_0811_134439.csv`, 145 columns x 9993 rows.

## Clean

- **No exceptions from our code.** The three NREs in the window are other mods: `FirstPerson.EVABoundFix`
  (already recorded in CLAUDE.md as not ours) and two from `Parallax` on scene teardown at 14:14:57.
- **Nothing separated all flight.** Mass sat at 5.247 t from MET 0.2 to the end, one step. That is
  independent confirmation that the trunk never left - fault F7 - from a column that knows nothing
  about decouplers.

## F8 · The mission telemetry froze after MET 53 and was written stale for 99% of the flight

`m_stationKm` and `m_closingMps` last changed at **MET 53**. Every one of the next ~6700 rows carries
`13.71 km, closing -127.47 m/s` unchanged - through the phase-down, the de-orbit, the failed
jettison and 22 minutes of coasting.

`FlightRecorder` reads `StationApproach.RangeM` and `.ClosingMps` directly, and deliberately so:
*"StationApproach's OWN numbers, not a second computation of the same thing."* That is the right
rule. But `Tick` returned early when not engaged, so those fields kept whatever they held when the
crew last disengaged, and the recorder faithfully wrote a remembered number 6700 times.

**The same shape as the docking refusal that started all of this: a true statement about a stale
variable and a false one about the world.** Fixed by measuring instead of returning - a new
`Observe()` that writes the same fields from the same `RelativeMotion.Of`, so it is still one source.

## F9 · The rendezvous leg displayed was `MatchOrbit` — the dead one

`m_rndz` reads **`MatchOrbit`** at MET 24 and 50. `Approach.LegFor` classifies on semi-major axis, our
orbit was 182 x 81 against a station at 86.3, so it correctly said the orbits do not match - and then
named the leg after `StMatchStationOrbit`, which is dead by decision and which nothing would ever fly.
The screen was reporting a leg that did not exist.

This is the display half of the same error as the banner correction: the classifier still assumed the
ladder had a MatchOrbit rung. **Leg 0 now fills it**, so the name has a live branch behind it again.
