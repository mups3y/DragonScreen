## B3 · THE LEAN IS CONDITIONAL IN F9I AND WAS UNCONDITIONAL IN OURS

**The descent got WORSE after the last change**, which is how this was found:

| | 08-11 16:03 | 08-12 09:32 |
|---|---|---|
| DESCENT attErr avg / max | 12.1° / 53.3° | **12.5° / 51.9°** |
| pitch actuation saturated | 30% | **35%** |
| yaw actuation saturated | 25% | **44%** |
| `b_leanFrac` max | — | **0.838 = tan(40°)** |

`BOOSTER.ks:360-364`, the whole of `LandingZoneGuidance`'s aim:

```
local result is velVec + errorVec.
if (vAng(result, velVec) > F9L_AOA) {
    set result to velVec:normalized + tan(F9L_AOA) * F9L_ErrScale * errorVec:normalized.
}
```

**F9I normally flies the naive sum.** `velVec` is retrograde at full speed — hundreds of m/s — and
`errorVec` is an impact error in metres, so the sum leans by `atan(error / speed)`: a few degrees
for a small miss, growing smoothly. The rebuild fires only when that natural lean already exceeds
the allowed angle, and clamps it back. **The angle of attack is a limiter on a proportional law.**

Ours had no conditional. Every tick commanded `tan(aoa) * scale` — the full clamped lean, whatever
the error. Below 4 km `aoa` is `alt/100`, so at 4 km the guidance demanded **40°** of lean from a
stage that needed two.

**My own comment talked me out of this.** `LeanFraction`'s doc described the conditional correctly
and then said the rebuild happens *"nearly always, because the naive sum compares metres of error
against metres per second of velocity and is meaningless when the error is large"*. The second half
is true; the "nearly always" was an assumption I never checked. At 250 m/s a 100 m error leans
21.8°, well under every ceiling in the schedule. Port rule 2 in one line — **I took F9I's constant
and wrote my own mechanism around it.** Both comments are now corrected.

Replayed against this flight's own descent: mean commanded lean 17.5° → 15.6°, peak **40° → 29°**.

### And the AoA comment had the source backwards

It claimed a clamp to 15° *"has never actually been in force"*. `BOOSTER.ks:455-459`:

```
wait until ship:altitude < 4000.
until (F9L_TrueRadar <= (F9L_StopDist + F9L_BoosterHeight)) {
    if (F9L_AOA > 15) { set F9L_AOA to 15. }
    if (ship:altitude < 10000) { set F9L_AOA to (alt:radar / 100). }
}
```

The loop is entered only below 4 km, so the second line always fires and the clamp is overwritten
before use. Above 4 km `F9L_AOA` is the 15 set at :437. The schedule is right; the reasoning
recorded next to it was not, and it is what justified reading 40° as a demand.

## B4 · TWO IMPACT PREDICTIONS IN ONE FILE, AND THE GUIDANCE USED THE WRONG ONE

`PredictedMiss` — the number on the screen — prefers `ImpactPredictor.Predict` whenever the vehicle
has reported its drag, falling back to a vacuum parabola only when it has not.

`ImpactErrorHoriz` — **the number the descent guidance steers on** — was a private second copy of
that fallback and never called the predictor at all. Same quantity, same class, forty lines apart,
different physics.

A vacuum solve in atmosphere predicts long and, worse, predicts *unsteadily*: it multiplies current
horizontal velocity by a free-fall time, so every m/s the airflow removes swings the answer by tens
of metres. The stage's ballistic coefficient was sitting in the recorder the whole descent at
`r_bcBooster` **1116–1516**, measured and unused.

Both now go through one `ImpactPointHoriz`. CLAUDE.md check #2 in its most literal form.

### What the recorder showed, and one correction to my own reasoning

`b_predMissKm` oscillates 45 → 287 → 45 → 248 m on a ~5 s cycle, and it is **smooth** — 11 m per
0.2 s sample — so it is a real closed loop, not sensor noise. Each pass through zero reverses the
error direction and flips the commanded lean side to side; attitude error jumps 8° → 27° in a
single sample as the command flips.

⚠ **But `b_predMissKm` is `PredictedMiss`, the drag-aware one, which the guidance was NOT using.**
So that trace is a symptom — the stage swinging swings its own velocity vector and therefore its
predicted impact — not direct evidence of what the guidance saw. The guidance saw the vacuum
number, which at 25 km is worse. Stated because I nearly reported the trace as the cause.

## L1 · Three working controls were unreachable behind a leftover guard

```
10:05:44  panel: DEPRESS RESPONSE - no KSP system behind this control
10:05:47  panel: SURPRESS FIRE   - no KSP system behind this control
10:05:50  panel: FIRE RESPONSE   - no KSP system behind this control
```

`pure/VehicleSystems.cs` models cabin depressurisation and fire, and `FlightCommands` has complete
handlers for all three — isolate the cabin, discharge the bottle, run the fire procedure. They were
never reached: `PanelButtons` tested `PanelMap.IsInert` first and returned. The list was written
when stock KSP genuinely had nothing behind them, and it outlived that fact.

Gate removed, `IsInert` deleted. If a control ever genuinely has nothing behind it the honest answer
is the refusal path everything else uses — `FlightCommands` returns false and the dash goes red.

## L2 · My propellant gate refused a capsule that needed nothing

```
10:05:29  REFUSED - 0.0 units of monopropellant cannot reach the atmosphere; that needs 0.0.
```

`EntryInterfaceMonoUnits` correctly returns **0** for a capsule already on an entry trajectory —
periapsis was −88.7 km. The gate then compared `0.0 < 0.0 + MonoFloorUnits` and refused it for
lacking a 5-unit ullage reserve against a burn it was not going to make. Logged three times.

Now gated on `EntryInterfaceUnits > 0.0`, with a test.
