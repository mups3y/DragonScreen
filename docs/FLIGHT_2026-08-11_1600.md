## R1 · The propellant refusal I added last round fired and stopped nothing

This is a regression, it is mine, and it is the reason the flight did not go to plan.

```
16:12:12.956  phase-down engaged: 85.7 x 83.7 km -> 85.1 x 79.2 km, about 4.2 m/s
16:12:12.957  DE-ORBIT engaged - have 71.1, need 150.7 ... margin -79.6 units
16:12:12.957  [ERR] REFUSED - 71.1 units cannot pay for a 78.7 unit de-orbit burn.
                    Nothing burned - the capsule is left in orbit with what it has.
16:12:12.958  phase-down engines lit - 228.0 kN          <-- one millisecond later
16:13:31.196  phase-down complete - ON THE LANDING ORBIT - 85.4 x 79.4 km
```

**"Nothing burned" was false.** `PhaseDownOps.Engage(v)` runs at `DeorbitOps.cs:140`; I put the
budget gate at :160, twenty lines *below* it. Setting `DeorbitOps.Engaged = false` does not stop
`PhaseDownOps`, which had already been handed the vessel. It flew both burns and parked the capsule
on the landing orbit with no de-orbit to follow.

A guard that fires and changes nothing is worse than no guard at all: the log said one thing and the
vehicle did another. **Fixed by moving the gate above every line that mutates state** — it needs
only `v`, so there was never a reason for it to be down there.

## R2 · And it refused on the wrong number

`have 71.1 ... cannot pay for a 78.7 unit de-orbit burn`. That 78.7 is `DeorbitMonoUnits`, the cost
of driving periapsis to **minus 31.8 km** — deliberately deep, because the entry guidance wants
margin to trim away. It is not the cost of getting home.

Reaching the 40 km entry interface costs roughly a third of that. **The capsule had ample
propellant to come home and was told it did not.** Refusing a de-orbit strands the crew, so the bar
has to be what is physically impossible, not what will land badly.

New `ReturnBudget.EntryInterfaceMonoUnits`, using the 40 km figure `FlightCommands` already uses for
WATER DEORBIT — a number this code path trusts, flown at 16:16 on this very flight and reported
`target periapsis reached`. So:

- **cannot reach the atmosphere** → refusal
- cannot reach the aim point → warning, the landing will miss long
- cannot cover entry + landing reserve → warning, as before

Five tests pin it, including the 71.1-unit case that was wrongly refused and a 2-unit case that must
still be.

## The deeper thing the numbers say

The capsule reaches orbit with **71 units of 195**. The S2 separates at 86.0 × **−118.8 km** and the
Dracos spend ~209 m/s closing the orbit themselves — `Dracos armed - the capsule closes its own

capsule that was low on propellant **exactly as the mission intends it to be at that point**.

# Booster descent stability — measured, 2026-08-11 16:03

Reported: *"quite unstable during its landing approach after the atmosphere braking burn. It will
swing side to side when it should be straight down and stable. There are also rotations/roll from
booster separation until landing."*

Both are real, both are in the recorder, and both are divergences from `BOOSTER.ks` rather than
tuning problems.

## The measurement first

Per phase, attitude error and actuation across the 251 s of booster flight:

| phase | attErr avg / max | pitch actuation saturated |
|---|---|---|
| BOOSTBACK | 0.2° / 1.8° | — |
| ENTRY BURN | 2.5° / 15.5° | — |
| **DESCENT** | **12.1° / 53.3°** | **30% of rows at ±1.00** |
| LANDING BURN | 4.6° / 14.4° | — |

Under power it is excellent. In DESCENT — engines off, the phase right after the entry burn — it
limit-cycles on a ~4 second period, and yaw is saturated a further 25% of the time. Roll actuation
never saturates at all, so roll authority was never the issue.

**The raw 5 Hz trace says the vehicle is not what is moving:**

```
   t     attErr    omegaP        actP   actY
 14.6      1.3      0.044        0.55   0.05
 14.8      1.7      0.044        0.62   0.11
 15.0     29.1      0.045       -1.00   1.00     <-- 27 degrees in one 0.2 s sample
 15.6     53.3     -0.049       -1.00   1.00
```

A 27° change in attitude error in 200 ms with a body rate of 0.045. **The stage did not move. The
target did.** The controller then correctly slams to full deflection chasing it, the stage really
does start swinging, the target jumps back, and it repeats all the way down.

## B1 · The lean was scaled on downrange, not on the error it steers along

`BoosterRecovery` built the descent aim as `dir + lean * errHoriz.normalized`, taking the DIRECTION
from the predicted-impact error and the MAGNITUDE from `s.DownrangeM`. F9I scales both on the same
vector:

```
BOOSTER.ks:359   local F9L_ErrScale is min(1, errorVec:mag / F9L_GuidanceDeadband).   // 5 m
BOOSTER.ks:363   velVec:normalized + tan(F9L_AOA) * F9L_ErrScale * errorVec:normalized
```

**That identity is the entire stability argument.** As the impact error goes to zero its direction
becomes meaningless — a predicted impact point that jitters by a metre swings its azimuth through
tens of degrees — but F9I multiplies that noisy direction by a scale going to zero at the same
moment, so the command stays still.

Scaling on downrange breaks the cancellation. Downrange is never small: `min(1, 600/5)` pins the
scale at **1.0**, and the guidance commands a full 15° lean along an azimuth that is numerical
noise. Our own `GuidanceDeadbandM = 5.0` is F9I's exact constant and its comment describes exactly
the right behaviour — *"inside this the steering authority winds down linearly"* — **it was simply
never handed a quantity that could get inside it.**

One argument changed. `LeanFraction(errHoriz.magnitude, aoa)`.

## B2 · The descent had no roll reference; F9I commands one

The existing note said roll is deliberately unconstrained because a local-vertical reference turns
the grid fins out of plane. That is right **about the flip**, and it was then applied to the whole
descent. F9I ends every `LandingZoneGuidance` call with a roll reference:

```
BOOSTER.ks:365   if F9L_LandingRoll < 0 { return lookdirup(result, facing:topvector). }
BOOSTER.ks:366   local _rollRef is heading(F9L_LandingRoll, 0):vector.
BOOSTER.ks:367   if vang(result, _rollRef) < 15  { return lookdirup(result, facing:topvector). }
BOOSTER.ks:368   if vang(result, _rollRef) > 165 { return lookdirup(result, facing:topvector). }
BOOSTER.ks:369   return lookdirup(result, _rollRef).
```

`F9L_LandingRoll is 0`, so the reference is heading 000 — **horizontal north**. That is not the
local vertical the old warning is about and it does not turn the fins out of plane; it pins them to
a fixed plane against the ground. "Holding" the launch roll is passive — nothing commands it back,
so every disturbance from separation onward accumulates, which is the rolling that was reported.

Both escapes are ported and both matter: `lookdirup` has no answer when the aim is parallel to the
reference, and a stage standing vertically over its pad is parallel to a horizontal one. Outside
15°–165° the roll is left alone.

## Tests

The three existing lean tests could never have caught B1 — they call `LeanFraction` with the correct
argument, and the fault was the caller passing a different quantity. So the new tests pin the
**property** instead: the worst-case commanded swing if the error direction fully reverses,
`2·atan(LeanFraction(e, aoa))`, which must go to zero with the error.

| error | worst-case aim swing |
|---|---|
| 500 m | 30.0° — allowed, there is a real correction to make |
| 5 m | bounded at the deadband edge |
| 1 m | < 7° |
| 5 cm | < 0.5° — the noisy azimuth cannot be felt |

Plus the counter-case stated explicitly, so the regression is unmistakable: a downrange-like number
in the error's place leaves a 30° swing **on a perfect track**.

## Note on what was already good

None of this touched the controller, and nothing should. Attitude error was 0.2° through boostback
and 2.5° through the entry burn on the same gains — the cascade is not the problem and never was.
The landing was accurate before these changes (0.0 km downrange, 1 m/s); this is about it looking
and behaving the way it already flies.
