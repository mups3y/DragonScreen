### 🔴 FINDING H1 (upgraded from hypothesis — see below) — a TESTED, DOCUMENTED roll-reference safety
### margin exists as constants and is never wired into flight code
`Landing.cs:999-1007`: `RollRefMinDeg = 15.0, RollRefMaxDeg = 165.0` — the doc comment is explicit and
precise: *"the landing roll reference is used only when the aim is between these angles from it...
outside this band the roll must be left alone or the command is a singularity."* Cites `BOOSTER.ks:
367-368`, the exact escapes read earlier this session in the (now-superseded, correctly so) old
comment about `FlipDeg`'s roll handling. **Confirmed via grep: these two constants are referenced
NOWHERE except their own definition and three `FlightTest.cs` assertions that check their VALUES
(`5.0 < RollRefMinDeg`, `170.0 > RollRefMaxDeg`, `45.0` falls inside the band) — never their
APPLICATION.** Nothing in `BoosterRecovery.cs`'s `Aim()` or `AttitudeController.SteerTo` tests whether
the current roll reference is within this band before using it. The 4704-check docking-controller test
suite and this project's broader test discipline gave false confidence here: the tests prove the
CONSTANT has sane bounds, not that flight code ever consults it.

**And the gap is precisely measurable, not just missing.** `AttitudeController.SteerTo`'s own generic
degenerate-fallback (line 197) only triggers when `|Dot(up, targetForward)| > 0.999` — within
`acos(0.999) ≈ 2.56°` of EXACT parallel. F9I's own comment explains why their band is nearly 6x wider:
*"a booster standing vertically over its pad is exactly parallel to a horizontal north reference"* —
i.e. NEAR-parallel is common in normal flight, not just a single exact-degenerate instant, and the
danger zone is the whole 15° either side, not just the last 2.56°. **Between roughly 2.56° and 15°
from parallel (and symmetrically near 180°), NEITHER guard fires**: `SteerTo` computes
`targetTop = Vector3d.Exclude(targetForward, up).normalized` from a genuinely near-degenerate cross
product, which is numerically noisy — a small change in the aim direction swings the excluded
residual through a large angle. This refines the original hypothesis (which framed the failure as
purely "near-zero commanded roll") into something that also explains the OTHER half of the symptom:
tonight's data showed both long spans of near-zero roll actuation AND sharp, erratic roll-rate swings
(instantaneous rates up to 15-18°/s with no sustained direction) — consistent with the aim direction
drifting in and out of this un-guarded near-parallel zone, sometimes landing close enough to trigger
`SteerTo`'s narrow fallback (re-seeding to current position → near-zero commanded error) and sometimes
sitting in the wider gap F9I's band was built to cover (→ a noisy, swinging reference).

**Still not fully verified — the missing piece is the same as before**: confirming that
`BoosterRecovery.Aim`'s `dir` (retrograde plus the guided lean) actually spends meaningful time within
this ~2.56°-15° gap during the coast requires either new instrumentation (log
`Vector3d.Angle(flipAxis, dir)` or the `SteerTo` fallback firing) or a direct trajectory derivation —
this audit did not add that instrumentation or fly a confirming flight. But the MECHANISM is no longer
speculative: a documented, F9I-sourced, unit-tested safety margin for exactly this failure mode exists
in the codebase and is provably never applied where the comment says it must be.

**The likely correct fix, once verified**: apply `Landing.RollRefMinDeg`/`RollRefMaxDeg` as a gate in
`BoosterRecovery.Aim` before passing `upHint = -flipAxis` to `SteerTo` — if the angle between `dir` and
`-flipAxis` falls outside the band, pass `Vector3d.zero` (hold current roll) instead, exactly as F9I's
two escapes do. This is DIFFERENT from both reverted attempts tonight: the HoldRoll (rate-damping
always, unconditionally) was too broad and removed active roll control everywhere, including where the
reference is perfectly healthy; this would only disengage the reference in the specific, narrow,
provably-in-the-source-as-a-known-hazard geometric zone. Still needs verification before flying it —
one more guessed roll fix would be the third this session.

**⛔ THE EXACT FIX SITE, CONFIRMED BY READING IT — and the comment already describes it in full.**
`BoosterRecovery.cs:1544-1565` — the block immediately above where `upHint` is set — QUOTES F9I's
escape logic verbatim:
```
BOOSTER.ks:367  if vang(result, _rollRef) < 15  { return lookdirup(result, facing:topvector). }
BOOSTER.ks:368  if vang(result, _rollRef) > 165 { return lookdirup(result, facing:topvector). }
```
and states outright: *"The two fallbacks are not optional... on an RTLS the stage IS pointed
near-vertically while the reference is horizontal only when it is nearly on top of the pad - so both
the 15 and the 165 degree escapes fire in normal flight, and both mean 'keep the roll you have'."*
Then, ~40 lines later in `BoosterRecovery.Aim` (as it stood on 2026-08-18), it sets `upHint`:
```csharp
Vector3d upHint = (flipSeeded && flipAxis.sqrMagnitude > 0.5) ? -flipAxis : Vector3d.zero;
```
— a plain binary check with **no angle test at all**. The 15°/165° logic the comment just spent 20
lines explaining is simply not there. `Landing.RollRefMinDeg`/`RollRefMaxDeg` are the exact constants
for this exact check, sitting unused one file away. **This is no longer a hypothesis about where the
gap might be — it is the gap, in the function the comment names, described by the comment that sits
directly above it.** Even the 2026-08-18 note in `BoosterRecovery.Aim` (written THIS session,
after tonight's reverted HoldRoll attempt) says *"the real fix is still open... measure the aero roll
torque during the coast first"* — written without noticing the answer was already spelled out 40 lines
above it. **Concrete patch** (still unflown, still needs verification, not applied by this audit):
```csharp
Vector3d refAxis = (flipSeeded && flipAxis.sqrMagnitude > 0.5) ? -flipAxis : Vector3d.zero;
Vector3d upHint = Vector3d.zero;
if (refAxis.sqrMagnitude > 0.5)
{
    double angleToRef = Vector3d.Angle(dir, refAxis);
    if (angleToRef >= Landing.RollRefMinDeg && angleToRef <= Landing.RollRefMaxDeg)
        upHint = refAxis;
}
```

*(Reasoning trail: this finding started as a hypothesis — that `SteerTo`'s degenerate-fallback might
re-seed the roll target to "wherever the vehicle already is" on consecutive ticks, producing near-zero
commanded error while the vehicle rolls freely. Reading `Landing.cs` straight through in this pass
found F9I's own answer to exactly that failure mode already sitting in the codebase as tested,
never-applied constants — which turned the hypothesis into the confirmed gap above, and additionally
explained the noisy/swinging half of the symptom the original framing didn't cover.)*

### 🔴 FINDING H2 — CONFIRMED FROM DATA: the controller itself believes roll has ~10x less torque
### authority than pitch/yaw during the booster coast. Root cause of the ASYMMETRY not yet settled.
`AttitudeController.AddRcsTorque` is only invoked for `pm as ModuleRCS` (`AvailableTorque`, line 462).
The actual parts on the flown craft use **`ModuleRCSFX`**, confirmed in

even succeeds. **Checked directly against the recorder's own `b_torqueX/Y/Z` columns** (exactly

Two explanations remain open and are NOT distinguished by any data or tool available this session:
- **Genuine vehicle geometry** — a real booster's RCS quads may simply have a much weaker roll moment
  arm than pitch/yaw, in which case 33.6 kN·m is an honestly-reported, correct fact about this craft.

**This asymmetry does not, by itself, explain the near-zero ROLL ACTUATION observed** (33.6 kN·m of
